## 2. P0 — CSV 선택 후 화면 상태를 명확하게 전환

### 2-1. 파일 선택 전 (`empty`)
- 큰 드롭존과 `CSV 파일 선택` 버튼, 형식 요건 안내를 보여준다.
- `데이터 품질 진단하기`는 파일이 없으면 실행되지 않아야 하고, 이유를 사용자에게 알린다.

### 2-2. 파일 선택 후 (`selected`)
- 큰 드롭존을 **간결한 선택 파일 카드**로 교체하거나 축소한다. 원래 드롭존이 그대로 화면 대부분을 차지하지 않게 한다.
- 파일명, 크기, 선택 상태를 표시한다. 사용자가 브라우저에서 파일을 선택한 상태인지, 서버에 실제로 수신·저장된 상태인지 **정확하게 구분**한다.
- `파일 변경` 및 `선택 취소` 버튼을 제공한다. 파일 변경을 누르면 파일 선택기가 열리며, 선택을 취소하면 새 파일을 고르기 전 상태로 돌아간다.
- 업로드 관련 설정(건물 ID, 시간대, CSV 시간 표기 방식)은 계속 수정 가능하게 한다.
- 다음 주요 행동은 하나: `데이터 품질 진단하기`.
- 파일명은 길면 줄임표와 전체 이름 확인 경로를 제공하고, 모바일에서도 겹치지 않게 한다.

### 2-3. 파일 교체·선택 취소의 상태 정책
- 파일 input의 실제 값을 해제하여 같은 파일도 다시 선택할 수 있게 한다.
- 선택된 파일과 **그 파일/설정에 종속된** 프론트엔드 품질 진단 결과, WARNING 동의, 학습 가능 플래그 및 임시 오류 상태를 적절히 초기화한다.
- 파일 교체나 시간대·시간 해석 모드 변경 후 옛 진단 결과를 새 파일의 결과처럼 표시하지 않는다.
- 검증 API 요청이 진행 중에 파일을 교체·해제하면 이전 요청의 늦은 응답이 새 상태를 덮어쓰지 않도록 요청 식별자나 요청 취소/무시 정책을 적용한다.
- **기존 서버 저장 모델·학습 기록을 묵시적으로 삭제하지 않는다.** 브라우저의 `선택 취소`와 서버의 `저장 데이터 영구 삭제`는 별도 기능이다. 서버 삭제 API가 없다면 임의로 있다고 가정하지 말고 보고서에 명시한다.

### 2-4. 품질 진단 중·완료 후
- 진단 요청 중: `품질 진단 중...`과 진행 상태, 중복 제출 방지, 적절한 접근성 알림을 제공한다.
- PASS: 실제 진단값/기간을 표시하고 학습 시작을 활성화한다.
- WARNING: 구체적인 이유와 허용 정책을 보여주고, 해당 WARNING에 **실제 해당할 때만** 제한 실험 동의를 노출한다.
- FAIL: 실패 이유·수정 방법·파일 변경 또는 설정 재시도 CTA를 제공하며 학습 시작을 막는다.
- 화면에 진단 결과가 없을 경우 `진단 전`이라고 표시한다. 파일 선택만으로 PASS 처리하지 않는다.

## 3. P0 — 오른쪽 품질 진단 패널의 상태별 구성

스크린샷의 오른쪽 큰 패널은 내용이 거의 없는 채 높이만 차지한다. 왼쪽 업로드와 오른쪽 진단의 관계를 상태별로 명확히 바꾼다.

- 파일 미선택: 짧은 안내와 `CSV를 먼저 선택해 주세요` 메시지, 불필요한 대형 장식 빈 공간 최소화.
- 파일 선택됨·미진단: `선택한 파일` 요약(이름, 파일 크기) + `품질 진단을 실행해 주세요`. 데이터 기간·결측·연속성·학습 가능 여부는 **진단 전/확인 전**으로 표시.
- 진단 중: 결과 자리의 로딩 상태 표시.
- PASS/WARNING/FAIL: 실제 API 결과에서 확인된 기간, 누락, 연속성, 판정 이유와 다음 행동을 시각적 위계에 따라 표시.
- 파일 변경·취소 시 결과 패널도 새로운 현재 상태와 즉시 일치해야 함.
- 배경 Contour 그래픽은 보조 역할로 유지하되 정보 가독성을 방해하거나 과도한 빈 공간을 만드는 경우 강도·배치를 조정.

## 4. P0 — `explicit_offset` 오류를 이해하기 쉽게 표현

### 재현 조건
- 테스트 CSV: `energy_planner_test_office_2026-04_to_2026-10.csv` (시간별 214일, `timestamp`, `kwh`, **timestamp에 UTC 오프셋 없음**).
- `건물의 시간대`: `Asia/Seoul`.
- `CSV의 시간 표기 방식`: `CSV에 포함된 UTC 오프셋 사용`을 선택하고 진단하면 영어 오류가 노출되는 것으로 확인됨.

### 요구 동작
- 원인 메시지: `CSV에 UTC 오프셋이 포함되어 있지 않습니다.`
- 해결 안내: `‘시간대 정보가 없는 현지 시각’을 선택하고 다시 진단해 주세요.`
- 오류는 `CSV의 시간 표기 방식` 입력과 가까운 위치에 표시하고, 필요한 경우 해당 필드로 포커스를 안내한다.
- 실제 API 오류 코드는 내부 추적용으로 보존하되 UI에서는 사용자 친화적 한국어 메시지를 사용한다.
- 사용자의 확인 없이 시간 해석 모드를 조용히 변경하지 않는다. CSV 샘플 검사로 권장 모드를 제시할 수는 있다.
- 그 외 파일 인코딩·필수 열·음수·0 또는 비유한 값·시계열 중복·시간 간격 오류 등 기존 API 오류도 가능한 범위에서 원인과 해결 방법으로 매핑한다. 정책이나 숫자 기준은 변경 금지.

## 5. P1 — Workspace의 단계 이동 UX

- Workspace 내부 `CSV 업로드 → 품질 진단 → 모델 학습` 단계는 현재 단계를 잘 보이게 하고, 작업 완료 상태와 현재 보고 있는 패널을 **구분**한다.
- 현재 두 단계가 나란히 노출되는 레이아웃의 장단점을 실제 화면에서 평가한다. 화면이 길고 비어 보이는 문제가 지속되면 **상태 기반 Stepper + 현재 단계 단일 패널**로 개선한다. 단, 기존 정보 접근이 오히려 불편해지지 않도록 이전 완료 단계에 바로 복귀할 수 있게 한다.
- 단계 선택 자체가 품질 진단 API나 모델 학습 API를 실행해서는 안 된다.
- 학습 버튼을 누르기 전까지 학습은 시작되지 않도록 유지한다.
- FAIL에서 학습 불가를 명확히 보여주며, WARNING 동의는 적용 정책에 맞춘다.
- 화면 이동/새로고침 후 이미 서버에 존재하는 학습 작업을 실제 상태 조회 API로 복원한다. 없는 API를 꾸며내지 않는다.
- 단계 이동에 따라 버튼이나 경고가 화면 아래 숨기지 않도록 모바일을 포함해 검수한다.

## 6. P1 — 검색 가능한 건물 시간대 선택 UI

- 현재의 `Asia/Seoul` 자유 입력 필드를 도시명·국가명·IANA 식별자 검색이 가능한 UI로 개선한다.
- 예: `서울 → Asia/Seoul`, `뉴욕 → America/New_York`, `도쿄 → Asia/Tokyo`, `런던 → Europe/London`.
- 실제 요청 payload는 기존 백엔드가 기대하는 **IANA 식별자**를 유지한다. 입력 계약·시간 해석 모드(`iana_civil_time` / `explicit_offset`)는 유지한다.
- 사용자가 검색 목록에서 항목을 선택해야 확정되도록 하고, 키보드 탐색·모바일 터치·스크린리더를 고려한다.
- 백엔드가 지원하지 않는 시간대는 조용히 승인하지 않는다. 브라우저 지원 목록과 서버 목록이 다를 수 있으므로 서버 검증을 기준으로 처리한다.
- DST 중복·누락 시각 문제는 기존 검증 정책을 준수한다. 임의로 시간대 또는 타임스탬프를 보정하지 않는다.
- 시간대 변경 시 기존 진단 결과 재검증이 필요한지 현재 API 계약에 맞게 처리한다.
- 검색형 UI 구현이 서버 목록 부재 등으로 막히면 안전한 입력+자동완성 대안을 제시하고 기술적 제약을 보고한다.

## 7. P1 — 세 페이지 공통 이동·메시지 회귀 점검

**이미 반영된 한국어 카피·페이지 분리는 유지**한다. 다음은 실제 동작과 노출 분기를 검증하고 미흡한 경우만 고친다.

- 글로벌 메뉴: Home(`/`), Workspace(`/workspace`), Dashboard(`/dashboard`), `aria-current="page"`, 직접 URL·새로고침·뒤로 가기.
- 메뉴 이름을 `홈 / 데이터 분석 / 대시보드` 등으로 바꾸는 것은 별도 제안 사항이므로 **사용자 승인 없이 변경하지 않는다**.
- Home CTA `CSV 업로드 시작` → Workspace 진입.
- 파일 미선택 / 진단 실패 / 학습 중 / 모델 없음 / 모델 있음·예측 전 / 예측 완료 상태에 따라 기본 CTA는 하나를 강조한다.
- Dashboard 모델 없음: 가짜 128.4kWh 등 예시 수치를 실측·실제 예측처럼 노출하지 않는다. 적절한 데이터 준비 CTA 제공.
- Dashboard에 `CSV 업로드하러 가기`와 `데이터 분석으로 돌아가기`가 같은 상태에서 동시에 중복 표시되면 하나로 정리한다.
- 예측 실행은 기존 저장 모델로만 수행하며 자동 재학습하지 않는다.
- Validation 모델 선택과 Test 최종 평가 구분 및 kWh·MAE·WAPE 단위를 유지한다.

## 8. P2 — 건물 ID·로그인 연구는 구현 범위에서 분리

- 현재 `건물 ID`는 로그인 ID가 아니라 건물의 모델과 결과를 구분하는 키라는 설명을 유지한다.
- 빈 값·중복 값·다른 건물 결과 혼합 위험이 있는지 백엔드에서 조사하고 **기존 저장 경로/키를 임의 변경하지 않는다**.
- 사용자 친화적인 `건물 이름` 표시와 서버 생성 불변 `building_id`, `내 건물` 목록, 계정/접근 제어는 후속 설계 제안으로 보고한다.
- **이번 작업에서는 로그인·회원가입·계정 테이블·기존 결과 공개 조회·데이터 영구 삭제 API를 새로 구현하지 않는다.** 공개 배포를 전제로 한 다른 사용자 데이터 접근은 반드시 인증과 서버 측 권한 확인이 선행되어야 한다.

## 9. 구현 불변 조건

- 기존 HTML/CSS/JavaScript 프론트엔드 및 현재 백엔드 API 계약을 우선 유지한다. 프레임워크 전환 금지.

## 11. 작업 방식과 완료 보고

1. **현행 코드/화면을 먼저 읽고** 요구사항별 구현 상태 매트릭스를 작성한다.
2. 사용자 추가 결정이 필요하지 않은 P0와 관련 P1 작업을 묶어서 수정한다. 이미 구현된 기능은 중복 개발하지 않는다.
3. 기술적·정책적 결정이 필요한 부분(로그인, 건물 ID 체계 변경, 서버 데이터 영구 삭제 등)은 **구현하지 말고 제안/리스크로 보고**한다.
4. 자동 테스트 및 가능하다면 실제 브라우저 시나리오를 수행한다. 필요한 경우 테스트 전후 스크린샷을 저장한다.
5. 보고서는 다음 구조로 작성한다.
   - `반영 상태 표`: 항목별 기존 상태/수정 결과/근거
   - `변경 파일과 주요 로직`
   - `사용자가 보는 변경 전/후 문구와 화면`
   - `테스트 PASS/FAIL/미실행 및 재현 방법`
   - `남은 리스크`, 특히 서버에 저장된 업로드 파일 삭제 여부와 건물 ID/인증 범위
   - `추가 의사결정이 필요한 항목`

**최종 목표:** 파일을 선택한 사용자는 즉시 선택된 파일을 확인하고 변경·취소할 수 있어야 한다. 시간 해석 오류가 발생하면 한국어로 원인과 복구 방법을 이해해야 하며, 품질 진단에서 모델 학습과 예측으로 이어지는 흐름을 혼동 없이 이용할 수 있어야 한다.
