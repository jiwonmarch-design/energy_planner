# Energy Planner 건물별 신규 GRU 학습 명세

## 1. 문서 목적

이 문서는 건물별 신규 GRU 모델에 입력할 피처, 계산 시점, 입력 텐서와 데이터 누수 방지 규칙을 정의합니다.

확정된 방향:

- 건물마다 GRU를 처음부터 새로 학습
- 과거 168시간을 입력하고 다음 24시간을 직접 출력
- 입력 원천은 시간별 `timestamp`와 `kwh`
- 기상정보와 공휴일 제외
- 건물별 스케일러 독립 관리
- 스케일러는 Train 데이터로만 적합
- 최초 학습 후 모델·스케일러·피처 명세 저장
- 예측 요청에서는 저장된 산출물을 재사용
- 재학습은 별도의 명시적 작업으로 수행

기존 인턴 GRU의 26개 피처와 기존 가중치는 참고만 합니다. 신규 피처 명세는 기존 모델과 입력 크기·순서가 다르므로 기존 가중치와 호환되지 않습니다.

## 2. 예측 시점과 표기

예측 기준 시점을 `T`라고 정의합니다.

- 입력 시퀀스: `T-167`부터 `T`까지 168시간
- 예측 대상: `T+1`부터 `T+24`까지 24시간
- 입력 텐서: `X[T-167:T]`
- 타깃 벡터: `y[T+1:T+24]`
- 모든 입력 피처는 `T` 시점까지 확인된 값으로만 생성
- `T+1` 이후의 실제 kWh는 입력 피처에 포함하지 않음

timestamp는 1시간 소비 구간의 시작 시각이며, UTC로 환산한 시각을 연속성 검사와 정렬의 기준으로 사용합니다.

## 3. 피처 후보

### 3.1 전력량 피처

모든 rolling은 현재 입력 행 `t`를 포함하고 과거 방향으로만 계산합니다. `t`는 예측 기준 `T`보다 늦을 수 없습니다.

| 피처 | 계산 정의 | 역할 | 해당 행보다 추가로 필요한 과거 이력 | 스케일링 |
|---|---|---|---:|---|
| `kwh` | `kwh(t)` | 해당 입력 시각의 실제 소비량 | 0시간 | 적용 |
| `lag_1` | `kwh(t-1)` | 직전 시간 수준 | 1시간 | 적용 |
| `lag_24` | `kwh(t-24)` | 전일 동일 시간 수준 | 24시간 | 적용 |
| `lag_168` | `kwh(t-168)` | 전주 동일 시간 수준 | 168시간 | 적용 |
| `rolling_mean_3` | `mean(kwh(t-2), …, kwh(t))` | 단기 수준 완화 | 2시간 | 적용 |
| `rolling_mean_24` | `mean(kwh(t-23), …, kwh(t))` | 최근 하루 평균 | 23시간 | 적용 |
| `rolling_mean_168` | `mean(kwh(t-167), …, kwh(t))` | 최근 일주일 평균 | 167시간 | 적용 |
| `diff_1` | `kwh(t) - kwh(t-1)` | 직전 시간 변화 | 1시간 | 적용 |
| `diff_24` | `kwh(t) - kwh(t-24)` | 전일 동일 시간 대비 변화 | 24시간 | 적용 |

rolling 구간에 결측이 하나라도 있으면 해당 피처는 결측입니다. 최소 관측 수를 낮춰 부분 평균을 계산하지 않습니다.

### 3.2 시간 피처

시간 피처는 건물 현지 시각으로 계산합니다.

| 피처 | 계산 정의 | 범위 | 역할 | 스케일링 |
|---|---|---:|---|---|
| `hour_sin` | `sin(2π × local_hour / 24)` | -1~1 | 하루 주기의 연속 표현 | 미적용 |
| `hour_cos` | `cos(2π × local_hour / 24)` | -1~1 | 하루 주기의 연속 표현 | 미적용 |
| `weekday_sin` | `sin(2π × local_weekday / 7)` | -1~1 | 주간 주기의 연속 표현 | 미적용 |
| `weekday_cos` | `cos(2π × local_weekday / 7)` | -1~1 | 주간 주기의 연속 표현 | 미적용 |
| `is_weekend` | 토요일 또는 일요일이면 1, 아니면 0 | 0 또는 1 | 주말 운영 차이를 명시 | 미적용 |

`local_weekday`는 월요일 0부터 일요일 6까지 사용합니다.

`is_weekend`는 weekday 순환 피처에서 계산 가능한 중복 정보이지만 건물 운영의 평일·주말 구분을 모델에 직접 제공하는 저비용 피처입니다. 첫 실험에 포함하고, 후속 ablation 실험에서 제거 효과를 비교할 수 있습니다.

### 3.3 시간대 메타데이터

UTC 시각은 연속성 검사에 사용하고 IANA 시간대는 현지 hour와 weekday 생성에 사용합니다.

- 오프셋 없는 CSV: Phase 6-2 규격에 따라 IANA 시간대가 필수
- 오프셋 포함 CSV: 과거 행의 현지 시각은 오프셋으로 읽을 수 있지만 DST 규칙과 재현 가능한 향후 시각 생성을 위해 학습 메타데이터에 IANA 시간대를 함께 저장
- 오프셋과 IANA 시간대 규칙이 충돌하면 학습을 시작하지 않고 사용자 확인 요청
- DST로 같은 현지 시각이 두 번 나타나도 UTC 시각이 다르면 서로 다른 입력 행
- 반복된 현지 시각의 hour·weekday 값이 같아지는 것은 정상
- 존재하지 않는 현지 시각을 임의 생성하지 않음

피처 생성 관점에서는 `building_timezone`이라는 IANA 시간대 메타데이터를 학습 필수 항목으로 권장합니다. CSV 파일 컬럼으로 추가하지 않고 업로드 작업의 별도 메타데이터로 관리합니다. 이 요구사항을 입력 화면에 반영하는 방식은 후속 구현 설계에서 확정합니다.

## 4. A안: 단순 피처 구성

### 4.1 피처 순서

1. `kwh`
2. `hour_sin`
3. `hour_cos`
4. `weekday_sin`
5. `weekday_cos`
6. `is_weekend`

### 4.2 입력과 이력

- 피처 수: 6
- 입력 텐서: `[batch_size, 168, 6]`
- 단일 예측에 필요한 원본 이력: `T-167`부터 `T`까지 연속 168시간
- 단일 학습 조합에 필요한 원본 범위: 입력 168시간과 정답 24시간, 총 192시간
- 출력 텐서: `[batch_size, 24]`

### 4.3 장점

- GRU가 168시간 시퀀스에서 단기·일간·주간 패턴을 직접 학습할 수 있음
- 추가 lag warm-up 구간이 필요하지 않음
- 피처 정의와 운영 추론을 일치시키기 쉬움
- 결측 하나가 무효화하는 원본 범위가 B안보다 작음
- 스케일러와 입력 명세가 단순해 건물별 관리가 쉬움
- 첫 MVP에서 누수와 정렬 오류를 검증하기 쉬움

### 4.4 한계

- lag와 rolling을 명시적으로 제공하지 않음
- 데이터가 적으면 GRU가 전일·전주 반복 패턴을 충분히 학습하지 못할 수 있음
- `is_weekend`는 weekday 순환 피처와 일부 중복

## 5. B안: 확장 피처 구성

### 5.1 피처 순서

1. `kwh`
2. `lag_1`
3. `lag_24`
4. `lag_168`
5. `rolling_mean_3`
6. `rolling_mean_24`
7. `rolling_mean_168`
8. `diff_1`
9. `diff_24`
10. `hour_sin`
11. `hour_cos`
12. `weekday_sin`
13. `weekday_cos`
14. `is_weekend`

### 5.2 입력과 이력

- 피처 수: 14
- 입력 텐서: `[batch_size, 168, 14]`
- 입력 시퀀스 자체: `T-167`부터 `T`까지 168시간
- 가장 이른 입력 행 `T-167`의 `lag_168` 계산에 필요한 시각: `T-335`
- 단일 예측에 필요한 원본 과거 이력: `T-335`부터 `T`까지 연속 336시간
- 단일 학습 조합에 필요한 원본 범위: warm-up 168시간, 입력 168시간, 정답 24시간으로 총 360시간
- 출력 텐서: `[batch_size, 24]`

### 5.3 장점

- 전일·전주 수준과 최근 평균·변화를 명시적으로 제공
- 데이터가 충분할 때 반복 패턴을 학습하는 부담을 줄일 가능성
- 피처 중요도·제거 실험의 비교 대상이 명확함

### 5.4 한계

- GRU의 168시간 입력에 이미 포함된 정보를 중복 제공
- 피처 간 상관과 중복이 큼
- 학습 가능한 첫 시점이 168시간 더 늦어짐
- 결측이 warm-up, 입력창과 파생 피처에 전파되어 유효 표본이 크게 감소할 수 있음
- 학습·예측 정렬과 스케일러 관리가 복잡해짐
- 피처 수 증가가 정확도 개선을 보장하지 않음

## 6. A안과 B안 비교

| 비교 항목 | A안 | B안 |
|---|---|---|
| 피처 수 | 6 | 14 |
| 과거 원본 이력 | 168시간 | 336시간 |
| 학습 조합 총 원본 범위 | 192시간 | 360시간 |
| lag·rolling·diff | 없음 | 포함 |
| 결측 전파 | 상대적으로 작음 | 큼 |
| 구현 복잡도 | 낮음 | 높음 |
| 정보 중복 | 낮음 | 높음 |
| 첫 MVP 적합성 | 높음 | 비교 실험용 |
| 입력 shape | `[B, 168, 6]` | `[B, 168, 14]` |

## 7. 권장 피처 구성

첫 신규 GRU 실험에는 **A안**을 권장합니다.

선정 이유:

1. GRU 입력 자체가 과거 168시간의 kWh 시퀀스를 포함합니다.
2. 일간·주간 위치는 순환형 시간 피처로 표현할 수 있습니다.
3. 기존 26개 피처의 기상·공휴일·복잡한 파생 피처 의존성을 제거합니다.
4. B안의 `lag_168`과 `rolling_mean_168`은 추가 168시간 이력과 더 엄격한 결측 조건을 요구합니다.
5. 먼저 A안과 Last-24h·Last-168h를 비교해야 피처 확장의 필요성을 판단할 수 있습니다.
6. 단순 구성이 학습·예측 일관성, 재현성과 누수 검증에 유리합니다.

B안은 A안이 기준 모델보다 충분한 성능을 보이지 않거나 잔차 분석에서 전일·전주 정보 부족이 확인될 때 후속 실험으로 사용합니다. B안을 사용하더라도 기존 GRU 26개 피처를 복제하지 않습니다.

## 8. 스케일링 정책

### 8.1 스케일링 대상

A안:

- `kwh`

B안:

- `kwh`
- `lag_1`, `lag_24`, `lag_168`
- `rolling_mean_3`, `rolling_mean_24`, `rolling_mean_168`
- `diff_1`, `diff_24`

연속형 전력 피처는 건물별 Train 데이터에서만 평균과 표준편차를 적합하는 표준화를 기본 후보로 합니다.

### 8.2 스케일링하지 않는 피처

- `hour_sin`, `hour_cos`
- `weekday_sin`, `weekday_cos`
- `is_weekend`

순환형 피처는 이미 -1~1, 이진 피처는 0~1 범위이므로 기본적으로 별도 스케일링하지 않습니다.

### 8.3 타깃 스케일러

- 타깃 kWh 스케일러도 건물별 Train 타깃으로만 적합
- Validation과 Test는 `transform`만 수행
- 예측 출력은 저장한 타깃 스케일러로 역변환
- 새 예측 요청에서 `fit` 또는 `fit_transform` 금지
- 모델과 피처·타깃 스케일러의 버전을 하나의 산출물 단위로 저장

표준화 방식의 최종 채택과 상수 피처의 0분산 처리 방식은 Phase 6-6 학습 설정에서 확정합니다.

## 9. 학습 피처 생성 절차

1. CSV 입력 계약과 품질 정책을 통과한 데이터를 사용합니다.
2. timestamp를 UTC 실제 시각으로 정렬하고 1시간 연속성을 확인합니다.
3. IANA 시간대로 현지 hour와 weekday를 계산합니다.
4. 선택된 피처 버전 A 또는 B의 정의를 적용합니다.
5. 결측이 포함된 피처 행이나 연속되지 않은 입력창을 기록하고 제외합니다. 값을 채우지 않습니다.
6. 예측 기준 `T`별로 `T-167:T` 입력과 `T+1:T+24` 타깃을 구성합니다.
7. 시간순 Train, Validation, Test 표본을 확정합니다.
8. Train 입력과 Train 타깃으로만 스케일러를 적합합니다.
9. 동일한 저장 스케일러로 Validation과 Test를 변환합니다.
10. 확정된 피처 순서로 텐서를 생성합니다.

피처 계산은 인과적이므로 전체 원본 시계열에서 계산할 수 있지만, 피처 선택·스케일러 적합·모델 설정 결정에는 미래 구간 정보를 사용하지 않습니다. 분할 경계에서 과거 문맥을 공유하는 정확한 방식은 Phase 6-5에서 확정합니다.

## 10. 예측 피처 생성 절차

1. 저장된 모델의 피처 버전, 순서, IANA 시간대와 스케일러를 확인합니다.
2. A안은 최신 연속 168시간, B안은 최신 연속 336시간을 요구합니다.
3. 학습 때와 같은 timestamp 정렬, 현지 시간 변환과 피처 수식을 적용합니다.
4. 피처 이름과 순서가 저장 명세와 정확히 일치하는지 검사합니다.
5. 저장된 피처 스케일러의 `transform`만 사용합니다.
6. NaN·Inf와 시간 불연속이 없을 때만 `[1, 168, feature_count]` 텐서를 만듭니다.
7. 저장된 모델로 24개 출력을 생성하고 저장된 타깃 스케일러로 역변환합니다.
8. 최신 이력이 불완전하면 과거 창으로 대체하지 않고 예측 불가 사유를 표시합니다.

최초 학습 이후 일반 예측 요청은 저장 모델과 스케일러를 재사용합니다. 새로운 데이터로 모델을 갱신하려면 별도의 재학습 작업을 명시적으로 시작해야 합니다.

## 11. 데이터 누수 방지 규칙

금지 사항:

- `T+1` 이후 실제 kWh를 `T` 예측 입력에 포함
- 미래 방향 shift 또는 centered rolling 사용
- rolling 계산에 현재 입력 행보다 미래 시각 포함
- 전체 데이터로 스케일러 적합
- Validation 또는 Test로 피처 선택·하이퍼파라미터 조정
- Test 결과를 확인한 뒤 모델 선택을 변경
- 결측을 0, 평균 또는 보간값으로 임의 대체
- 시간 불연속 구간의 행을 이어 붙여 하나의 시퀀스로 생성
- A안 학습 모델에 B안 입력을 제공하거나 피처 순서를 변경
- 다른 건물의 스케일러를 재사용

허용 사항:

- 입력 행 `t`의 `kwh(t)`를 그 행의 과거 시퀀스 피처로 사용
- `t`와 그 이전 값만 포함하는 causal rolling
- Validation·Test 타깃 이전의 실제 168시간을 입력 문맥으로 사용하는 방식은 Phase 6-5에서 경계를 명시한 경우에만 허용
- Test는 모델 선택이 끝난 뒤 최종 평가에 한 번 사용

## 12. 저장 명세

건물별 학습 산출물에는 최소한 다음 정보를 함께 저장해야 합니다.

- 건물 또는 학습 작업 식별자
- 피처 명세 버전
- 피처 이름과 정확한 순서
- 입력 길이 168과 출력 길이 24
- IANA 시간대
- Train, Validation, Test 기간
- 피처 스케일러와 타깃 스케일러
- 모델 구조 설정과 가중치
- 데이터 품질 요약
- 학습·평가 지표
- 생성 시각과 코드 버전
- 원본 또는 학습 입력을 식별할 수 있는 해시

저장된 피처 수·순서·버전·스케일러 중 하나라도 맞지 않으면 모델을 실행하지 않습니다.

## 13. 기존 GRU와의 관계

기존 인턴 GRU는 26개 입력 피처와 `input_size=26`을 사용했습니다. 신규 권장 A안은 6개, B안은 14개이므로 다음 원칙을 적용합니다.

- 기존 가중치를 신규 모델에 로딩하지 않음
- 기존 피처 스케일러와 타깃 스케일러를 신규 건물에 사용하지 않음
- 기존 26개 피처의 기상·공휴일 정의를 복제하지 않음
- 기존 코드의 시퀀스 구성과 GRU 구조는 참고 가능
- 신규 모델은 독립 모델 설정과 독립 가중치를 생성

## 14. 미확정 사항

다음 항목은 이번 단계에서 확정하지 않습니다.

- `is_weekend` 제거 ablation 수행 여부
- B안 전체 적용 또는 일부 lag만 추가하는 중간안
- 표준화 방식과 0분산 처리
- 이상치 경고값을 학습에 유지할지 별도 승인할지 여부
- 분할 경계의 과거 문맥 공유 방식
- 구간별 최소 학습·평가 표본 수
- GRU hidden size, layer 수, dropout과 batch size
- epoch, learning rate와 early stopping
- 모델 채택 지표와 기준 모델 대비 최소 개선 폭
- 재학습 조건과 새 모델 교체 정책

## 15. 후속 작업

### Phase 6-5 시간순 데이터 분할 및 누수 방지

#### 15.1 분할안 비교

모든 기간과 경계는 UTC의 실제 경과시간으로 계산합니다. 아래 최대 조합 수는 결측이 없는 A안 데이터에 대한 이론값입니다.

##### A안: 마지막 30일 Test, 이전 30일 Validation

| 전체 기간 | Train | Validation | Test | 최대 Train 168+24 조합 | 비중복 Validation/Test 구간 |
|---:|---:|---:|---:|---:|---:|
| 90일 | 30일 | 30일 | 30일 | 529 | 각 30개 |
| 180일 | 120일 | 30일 | 30일 | 2,689 | 각 30개 |
| 365일 | 305일 | 30일 | 30일 | 7,129 | 각 30개 |

장점:

- Validation과 Test가 항상 같은 30일이라 건물 간 비교가 쉬움
- 180일 이상에서는 충분한 Train 기간 확보 가능
- 경계가 단순하고 설명하기 쉬움

단점:

- 90일 데이터는 Train이 30일뿐이며 잠정 최소 1,000개 학습 조합을 충족할 수 없음
- 짧은 데이터에 고정 60일을 평가용으로 사용해 Train 비중이 지나치게 작음

##### B안: Train 70%, Validation 15%, Test 15%

| 전체 기간 | Train | Validation | Test | 최대 Train 168+24 조합 | 비중복 Validation/Test 구간 |
|---:|---:|---:|---:|---:|---:|
| 90일 | 63일 | 13.5일 | 13.5일 | 1,321 | 각 최대 13개 |
| 180일 | 126일 | 27일 | 27일 | 2,833 | 각 27개 |
| 365일 | 255.5일 | 54.75일 | 54.75일 | 5,941 | 각 최대 54개 |

장점:

- 전체 기간이 달라도 일정한 비율 유지
- 90일 데이터에서도 Train 기간을 63일 확보
- 장기 데이터에서 평가 표본이 증가

단점:

- 평가 기간 길이가 건물마다 달라 지표 비교의 의미가 달라짐
- 365일 데이터에서는 Validation과 Test가 필요 이상으로 길어지고 Train이 줄어듦
- 경계가 날짜 중간에 생길 수 있어 사용자 설명과 운영 재현이 복잡해짐

비율 계산 결과가 1시간 단위로 나누어지지 않으면 UTC 시간 단위 절사·배분 규칙이 추가로 필요합니다.

##### C안: 데이터 기간에 따른 적응형 고정 평가 구간

| 전체 기간 | Train | Validation | Test | 최대 Train 168+24 조합 | 최대 겹침 Validation 조합 | 비중복 Validation/Test 구간 |
|---:|---:|---:|---:|---:|---:|---:|
| 90일 | 60일 | 15일 | 15일 | 1,249 | 337 | 각 15개 |
| 180일 | 120일 | 30일 | 30일 | 2,689 | 697 | 각 30개 |
| 365일 | 305일 | 30일 | 30일 | 7,129 | 697 | 각 30개 |

적응 규칙:

- 전체 관측 기간 90일 미만: GRU 학습 자격 `FAIL`
- 90일 이상 180일 미만: 마지막 15일 Test, 직전 15일 Validation, 나머지 Train
- 180일 이상: 마지막 30일 Test, 직전 30일 Validation, 나머지 Train
- 분할 후 최소 조합 수를 충족하지 못하면 기간이 충분해도 `FAIL`
- 90~179일 데이터는 조합 수를 충족해도 Phase 6-3 정책에 따라 `WARNING` 제한 실험

장점:

- 90일 데이터에서 최소 Train 기간을 보호
- 180일 이상에서는 건물 간 동일한 30일 평가 기간 유지
- 장기 데이터의 대부분을 Train에 사용
- UTC 기준 경계를 단순하게 재현 가능

단점:

- 90~179일과 180일 이상 데이터의 평가 기간이 다름
- 계절 전체를 평가하지 못할 수 있음
- 180일 경계에서 평가 기간이 15일에서 30일로 바뀜

#### 15.2 권장 분할 정책

MVP 초기 실험에는 **C안**을 권장합니다.

선택 이유:

1. 90일 데이터에서도 60일 Train을 확보해 잠정 최소 학습 조합을 이론상 충족할 수 있습니다.
2. 권장 기준인 180일 이상에서는 Validation과 Test를 각각 30일로 고정할 수 있습니다.
3. 365일 데이터에서 평가 구간이 과도하게 커지는 B안의 단점을 피합니다.
4. Train, Validation, Test의 역할과 기간을 사용자에게 설명하기 쉽습니다.
5. 향후 여러 건물 결과를 비교할 때 180일 이상 데이터는 같은 평가 길이를 사용합니다.

90일 데이터의 학습을 권장한다는 뜻은 아닙니다. Phase 6-3의 `WARNING` 상태와 PM의 제한 실험 승인이 함께 필요합니다.

#### 15.3 UTC 경계 정의

전체 시간축을 다음과 같이 정의합니다.

- `data_start`: 가장 이른 유효 UTC 시각
- `data_end_exclusive`: 가장 늦은 유효 UTC 시각 + 1시간
- 모든 구간은 시작을 포함하고 끝을 제외하는 반개방 구간 `[start, end)`
- `test_end = data_end_exclusive`
- `test_start = test_end - test_duration`
- `validation_end = test_start`
- `validation_start = validation_end - validation_duration`
- `train_start = data_start`
- `train_end = validation_start`

타깃 소속은 24시간 정답 전체로 판단합니다.

- Train 표본: `T+1 ≥ train_start`이고 `T+24 < train_end`의 마지막 시각까지 모두 Train에 존재
- Validation 표본: `T+1 ≥ validation_start`이고 `T+24 < validation_end`의 마지막 시각까지 모두 Validation에 존재
- Test 표본: `T+1 ≥ test_start`이고 `T+24 < test_end`의 마지막 시각까지 모두 Test에 존재

반개방 구간 표현에서는 타깃 마지막 시각 `T+24`가 각 `end`보다 작아야 합니다. 어떤 타깃도 두 구간에 걸칠 수 없습니다.

#### 15.4 180일 데이터 경계 예시

데이터가 `2026-01-01T00:00:00Z`부터 `2026-06-29T23:00:00Z`까지 완전하다고 가정합니다.

- `data_end_exclusive = 2026-06-30T00:00:00Z`
- Train: `[2026-01-01T00:00:00Z, 2026-05-01T00:00:00Z)`
- Validation: `[2026-05-01T00:00:00Z, 2026-05-31T00:00:00Z)`
- Test: `[2026-05-31T00:00:00Z, 2026-06-30T00:00:00Z)`

마지막 Train 타깃 예:

- 예측 기준 `T = 2026-04-29T23:00:00Z`
- 입력: `2026-04-23T00:00:00Z`부터 `2026-04-29T23:00:00Z`
- 타깃: `2026-04-30T00:00:00Z`부터 `2026-04-30T23:00:00Z`
- 타깃 24시간 전체가 Train 안에 있으므로 유효

첫 Validation 타깃 예:

- 예측 기준 `T = 2026-04-30T23:00:00Z`
- 입력: `2026-04-24T00:00:00Z`부터 `2026-04-30T23:00:00Z`
- 타깃: `2026-05-01T00:00:00Z`부터 `2026-05-01T23:00:00Z`
- 입력은 Train의 과거 실제값을 문맥으로 사용하고 타깃은 Validation에만 존재

첫 Test 타깃 예:

- 예측 기준 `T = 2026-05-30T23:00:00Z`
- 입력: `2026-05-24T00:00:00Z`부터 `2026-05-30T23:00:00Z`
- 타깃: `2026-05-31T00:00:00Z`부터 `2026-05-31T23:00:00Z`
- 입력은 Validation의 과거 실제값을 문맥으로 사용하고 타깃은 Test에만 존재

#### 15.5 과거 168시간 문맥 공유

Validation과 Test의 첫 예측부터 실제 운영과 같은 168시간 이력을 사용할 수 있도록 분할 이전 구간의 과거 관측을 문맥으로 허용합니다.

허용 규칙:

- Validation 입력은 예측 기준 이전의 Train 실제값을 포함할 수 있음
- Test 입력은 예측 기준 이전의 Validation 실제값과 이미 관측이 끝난 이전 Test 실제값을 포함할 수 있음
- 문맥 데이터는 입력으로만 사용하며 해당 표본의 타깃 소속을 바꾸지 않음
- Test 문맥을 사용한 순차 평가는 30일을 한 번에 예측하는 방식이 아니라 매 예측 기준 시점에 새로 확인된 실제값을 사용하는 rolling-origin 평가
- 모든 문맥 시각은 해당 예측 기준 `T` 이하이어야 함
- 문맥 값으로 스케일러를 다시 적합하거나 모델 가중치를 갱신하지 않음
- 결측 문맥을 Train 평균이나 예측값으로 채우지 않음

과거 문맥 사용은 미래 정보 누수가 아닙니다. 예측 시점에 이미 관측된 값만 사용하기 때문입니다. 반면 타깃 시각의 실제값, Test 전체 통계 또는 미래 결측 패턴을 모델 선택에 사용하는 것은 누수입니다.

#### 15.6 겹침 조합과 비중복 평가 구간

두 종류의 표본을 구분합니다.

##### 한 시간 이동 조합

- 예측 기준을 1시간씩 이동
- 인접 표본의 입력과 24시간 타깃이 대부분 겹침
- Train 학습과 Validation early stopping 손실 계산에 사용
- 15일 완전 Validation에서 최대 `360 - 24 + 1 = 337`개
- 30일 완전 Validation에서 최대 `720 - 24 + 1 = 697`개
- Validation 이전 문맥 168시간을 허용하므로 평가 구간 길이에서 168시간을 다시 차감하지 않음

##### 비중복 24시간 평가 구간

- 첫 타깃 시작을 분할 시작 UTC 시각에 고정
- 이후 타깃 시작을 정확히 24시간씩 이동
- 각 표본의 24시간 타깃이 서로 겹치지 않음
- Validation의 모델·기준 모델 비교와 Test 최종 평가의 주요 지표에 사용
- 15일 완전 구간에서 최대 15개, 30일 완전 구간에서 최대 30개
- DST와 무관하게 실제 UTC 24시간을 한 구간으로 사용하고 현지 시각은 표시용으로 함께 기록

평가 시작 시각 목록과 제외 사유는 모델 학습 전에 고정합니다. 데이터 완전성과 달력 위치만 사용하며 전력 사용량 크기, 예측값 또는 오차를 보고 날짜를 바꾸지 않습니다. 결측으로 무효인 고정 구간은 제외 사유를 남기고 다른 날짜로 사후 교체하지 않습니다.

#### 15.7 Validation 사용 구분

##### Early stopping 손실

- 모든 유효한 한 시간 이동 Validation 조합을 사용
- Train에서 적합한 스케일러로 변환
- 스케일된 24개 출력의 평균 L1 손실을 표본 전체에 집계
- epoch별 손실로 최적 체크포인트와 중단 시점을 결정
- patience, 최소 개선량과 최대 epoch는 Phase 6-6에서 확정

##### 모델 비교용 Validation 지표

- 미리 고정한 비중복 24시간 Validation 구간만 사용
- kWh로 역변환한 예측으로 MAE, RMSE와 후속 승인 지표 계산
- 동일한 구간에서 GRU, Last-24h와 Last-168h 비교
- 하이퍼파라미터와 최종 모델 선택은 Validation 결과로만 수행
- Test 지표는 선택 과정에 사용하지 않음

Early stopping 손실은 epoch 제어용이고, 비중복 Validation 지표는 모델·기준 모델 비교용입니다. 두 결과를 혼합해 하나의 지표처럼 보고하지 않습니다.

#### 15.8 Test 평가

- Validation에서 모델 설정과 체크포인트를 확정한 뒤 Test를 평가
- 미리 고정한 비중복 24시간 Test 구간을 주요 평가에 사용
- 선택된 GRU와 두 기준 모델의 지표를 같은 Test 구간에서 계산
- Test 결과를 확인한 뒤 피처, 하이퍼파라미터, 체크포인트 또는 평가 날짜를 변경하지 않음
- Test 기반 변경이 필요하면 기존 Test는 개발 자료로 전환하고 새로운 독립 Test 기간을 확보한 별도 실험으로 관리
- 겹치는 Test 조합의 결과는 진단 목적으로만 계산할 수 있으며 주요 채택 근거로 사용하지 않음

#### 15.9 스케일러 누수 방지

입력 스케일러:

- A안의 `kwh` 연속형 피처만 스케일링
- `hour_sin`, `hour_cos`, `weekday_sin`, `weekday_cos`, `is_weekend`은 스케일링하지 않음
- Train 구간의 고유 timestamp별 유효 입력 피처 행으로만 적합
- 겹치는 시퀀스를 펼쳐 같은 시각을 여러 번 가중하지 않음

타깃 스케일러:

- Train 구간에 속한 고유 timestamp별 실제 kWh로만 적합
- Validation과 Test 실제값을 평균·표준편차 계산에 포함하지 않음
- 겹치는 Train 타깃에 같은 시각이 반복되더라도 적합 통계에는 한 번만 사용

Validation과 Test:

- 저장된 Train 스케일러의 `transform`만 사용
- 과거 문맥이 Validation 또는 Test에 있더라도 스케일러 재적합 금지
- 건물마다 독립 스케일러 저장
- 다른 건물 또는 다른 분할 버전의 스케일러 사용 금지

출력 역변환:

1. GRU의 스케일된 출력 shape `[batch_size, 24]` 확인
2. 값을 `[-1, 1]` 형태로 임시 reshape
3. 저장된 타깃 스케일러의 `inverse_transform` 적용
4. 원래 `[batch_size, 24]`로 복원
5. kWh 단위에서 NaN·Inf와 shape 재검사

#### 15.10 잠정 최소 표본 기준

다음 수치는 MVP 초기 실험을 위한 **잠정 기준**입니다. Office 실험 결과에 따라 재검토합니다.

| 분할 | 표본 유형 | 잠정 최소 |
|---|---|---:|
| Train | 유효한 한 시간 이동 168+24 조합 | 1,000개 |
| Validation | early stopping용 유효한 한 시간 이동 조합 | 168개 |
| Validation | 비중복 24시간 모델 비교 구간 | 12개 |
| Test | 비중복 24시간 최종 평가 구간 | 12개 |

추가 조건:

- 모든 표본의 입력 168시간과 타깃 24시간이 실제 1시간 간격으로 완전해야 함
- 분할별 최소치 중 하나라도 미달하면 GRU 학습 자격 `FAIL`
- 90일 이상이라는 기간만으로 학습 가능 판정 금지
- Phase 6-3 `PASS` 데이터도 분할 최소치를 충족하지 못하면 `FAIL`
- Phase 6-3 `WARNING` 데이터는 최소치를 충족하고 PM이 제한 실험을 승인한 경우에만 학습 가능
- Phase 6-3 `FAIL` 또는 `CSV_FORMAT_FAIL` 데이터는 분할 검사 전에 학습 중지
- 이상치 의심값은 자동 제거하지 않으며 별도 승인 없이 표본 수를 늘리기 위해 보정하지 않음

12개 비중복 평가 구간과 168개 Validation 조합에는 아직 충분한 실증 근거가 없으므로 잠정값으로 기록합니다. Phase 7 Office 실험에서 안정성과 계절·요일 대표성을 확인한 뒤 조정합니다.

### Phase 6-6 통합 설계 및 구현 준비

#### 16.1 설계 상태와 변경 이력

Phase 6-5까지 확정한 A안 6개 피처와 C안 적응형 분할을 기준으로 학습 설정, 전처리, 파이프라인, 자동 검증과 산출물 구조를 통합합니다.

| 항목 | Phase 6-6 결정 | 상태 |
|---|---|---|
| 신규 GRU 크기 | hidden size 64, 2 layers | MVP 기본값 확정 |
| 입력·출력 | `[B,168,6] → [B,24]` | 기존 확정 유지 |
| 분할 | C안 적응형 UTC 분할 | 기존 확정 유지 |
| 스케일러 | 건물별 입력·타깃 StandardScaler 분리 | MVP 기본값 확정 |
| 모델 선택 | Validation만 사용 | 기존 확정 유지 |
| Test | 선택 후 1회 독립 평가 | 기존 확정 유지 |
| GRU 승격 최소 개선 폭 | best baseline 대비 5% MAE 개선 권장 | PM 결정 필요 |
| Test 후 전체 데이터 재학습 | 자동 수행하지 않음 | 보류 유지 |

기존 인턴 GRU의 hidden size 256, 3 layers와 기존 가중치는 신규 MVP 기본값으로 사용하지 않습니다.

#### 16.2 GRU 최종 권장 설정

| 설정 | 권장값 | 선택 이유 |
|---|---:|---|
| input size | 6 | 승인된 A안 피처 수 |
| lookback | 168시간 | 승인된 7일 입력 |
| output size | 24 | 다음 24시간 직접 출력 |
| hidden size | 64 | CPU와 소규모 데이터에 적합한 첫 모델 |
| GRU layers | 2 | 단일 layer보다 표현력을 확보하면서 복잡도 제한 |
| dropout | 0.1 | 2개 layer 사이에만 적용되는 완만한 규제 |
| batch size | 64 | 1,000개 이상 표본에서 안정성과 CPU 메모리 균형 |
| optimizer | Adam | 첫 실험에서 안정적인 기본 optimizer |
| learning rate | 0.001 | Adam의 보수적인 기본 시작값 |
| loss | L1Loss | MAE 방향과 일치하고 큰 오차에 MSE보다 덜 민감 |
| max epochs | 50 | 과도한 장기 학습을 제한 |
| early stopping patience | 7 epochs | 단기 변동으로 인한 조기 중단 완화 |
| minimum improvement | 0.0001 | 스케일된 Validation L1 기준 최소 개선량 |
| gradient clipping | global norm 1.0 | GRU의 기울기 폭주 방지 |
| random seed | 42 | 재현 가능한 기본값 |
| device | CPU 기본 | MVP 실행 환경 우선 |
| Train loader | shuffle=true, seed 고정 | 시간순 분할 후 표본 순서만 섞음 |
| Validation/Test loader | shuffle=false | 평가 순서 재현 |

early stopping은 `best_loss - current_loss ≥ 0.0001`인 경우만 개선으로 인정합니다. 7회 연속 개선이 없으면 중단하고 최저 Validation 손실 체크포인트를 복원합니다.

CPU 환경에서 실행 가능한 크기를 우선했지만 실제 학습 시간과 메모리는 아직 측정하지 않았습니다. 구현 단계에서 90일·180일·365일 합성 표본과 첫 Office 후보로 실행 시간을 기록해야 합니다.

#### 16.3 재현성 설정

구현 시 다음 seed를 모두 42로 고정합니다.

- Python random
- NumPy
- PyTorch CPU
- DataLoader shuffle generator

가능한 PyTorch 결정적 연산을 사용하고 실행 환경의 Python, PyTorch, NumPy와 scikit-learn 버전을 manifest에 기록합니다. 동일 환경·입력·seed의 반복 실행은 동일한 분할, 평가 목록과 허용 오차 내 동일한 예측을 생성해야 합니다.

CPU thread 수는 배포 환경 성능에 영향을 주므로 이번 문서에서 고정하지 않고 실행 환경 manifest에 실제 값을 기록합니다.

#### 16.4 입력·타깃 스케일러

입력과 타깃은 같은 kWh 원천을 사용하더라도 역할과 적용 shape가 다르므로 별도 스케일러로 관리합니다.

##### 입력 스케일러

- 방식: `StandardScaler`
- 대상: A안의 연속형 `kwh` 한 개
- 적합 데이터: Train 구간에서 입력 피처로 사용 가능한 고유 timestamp별 kWh
- 같은 시각이 겹치는 여러 시퀀스에 포함되어도 적합 통계에는 한 번만 포함
- 시간 순환형 4개와 `is_weekend`은 스케일링하지 않음
- 최종 6개 피처 순서는 저장 명세와 동일하게 재조립

##### 타깃 스케일러

- 방식: 입력과 분리된 `StandardScaler`
- 적합 데이터: Train 구간에 속한 고유 timestamp별 실제 kWh
- 겹치는 24시간 타깃에서 같은 시각이 반복되어도 적합 통계에는 한 번만 포함
- Phase 6-5의 “Train 기간 실제 kWh” 정의와 동일
- Validation과 Test 타깃은 `transform`만 수행

##### 상수와 0분산 처리

- Train 표준편차가 0인 피처는 `scale=1.0`으로 기록하고 변환값을 0으로 유지
- 상수 입력 또는 상수 타깃 상태를 `WARNING_CONSTANT_FEATURE` 또는 `WARNING_CONSTANT_TARGET`으로 기록
- 0으로 나누지 않으며 NaN·Inf를 만들지 않음
- 상수 타깃의 GRU 성능은 기준 모델과 함께 평가하고 자동 우수 판정하지 않음
- 상수 여부를 숨기거나 작은 임의 잡음을 추가하지 않음

##### 검사와 역변환

각 단계에서 다음을 검사합니다.

1. fit 전 Train 값의 shape와 NaN·Inf
2. fit 후 평균, 분산, scale의 유한성
3. transform 후 Train·Validation·Test의 NaN·Inf
4. 입력 텐서 shape `[B,168,6]`
5. 모델 출력 shape `[B,24]`
6. 출력을 `[-1,1]`로 reshape하여 target scaler `inverse_transform`
7. 역변환 후 `[B,24]` 복원
8. kWh 예측의 NaN·Inf와 음수 개수 기록

음수 예측을 0으로 자동 보정하지 않습니다. 음수 예측이 있는 GRU는 Validation 승격 후보에서 제외하고 원인을 보고하는 것을 MVP 기본 정책으로 사용합니다.

#### 16.7 학습과 체크포인트

- 모델은 매 run마다 새로 초기화하며 기존 인턴 가중치를 로딩하지 않음
- Train mini-batch로 forward, L1 loss, backward, gradient clipping, Adam step 수행
- epoch마다 전체 겹침 Validation loss 계산
- 최저 Validation loss의 `model_state_dict`만 best checkpoint로 보존
- 체크포인트는 CPU에서 안전하게 로딩 가능한 가중치 중심 형식 사용
- optimizer state는 중단 학습 재개 기능이 승인될 때만 별도 저장
- best checkpoint 복원 후 비중복 Validation 비교 수행
- 마지막 epoch 가중치를 best checkpoint 대신 사용하지 않음
- loss가 NaN·Inf가 되면 즉시 실패 처리하고 활성 모델을 변경하지 않음

#### 16.8 자동 검증 설계

| 번호 | 테스트 사례 | 예상 결과 |
|---:|---|---|
| 1 | 완전한 89일 데이터 | 품질 `FAIL`, split·학습 미실행 |
| 2 | 완전한 90일 데이터 | 60/15/15일, `WARNING`, 제한 실험 승인 필요 |
| 3 | 완전한 180일 데이터 | 120/30/30일, 비중복 평가 각 30개 후보 |
| 4 | 결측으로 1,000/168/12/12 중 하나 미달 | 학습 자격 `FAIL` |
| 5 | 경계 직전·직후 타깃 생성 | 각 24시간 타깃이 한 분할에만 존재 |
| 6 | 미래 kWh를 변경한 복제 데이터 | 변경 시점 이전 입력 피처와 예측 입력이 동일 |
| 7 | Validation/Test에 극단값 삽입 | Train scaler 평균·분산이 변하지 않음 |
| 8 | batch 1과 batch N 추론 | 출력 shape 각각 `[1,24]`, `[N,24]`이며 모두 유한 |
| 9 | 다른 building ID의 scaler·model 조합 | manifest 식별자 불일치로 로딩 거부 |
| 10 | 동일 입력·환경·seed로 두 번 학습 | 동일 split·평가 일정·checkpoint epoch와 허용 오차 내 예측 |
| 11 | 최신 168시간 중 한 시각 누락 | 저장 모델이 있어도 추론 거부 |
| 12 | Test 지표가 Validation 순위와 다름 | 모델 재선택 금지, Test 결과만 보고 |
| 13 | Train kWh가 상수 | `FAIL_TRAIN_ZERO_VARIANCE`로 학습 전 차단 |
| 14 | GRU에 음수 예측 존재 | 자동 clipping 금지, 승격 후보 제외 |
| 15 | 기존 인턴 model path 주입 | 신규 run 로딩 정책에서 거부 |

미래값 방지 테스트는 `T+1` 이후 값을 변경해도 `T`까지의 A안 피처와 입력 텐서 해시가 같음을 확인합니다. 스케일러 누수 테스트는 Validation/Test 값만 변경한 두 데이터셋에서 Train scaler 통계와 변환된 Train 텐서가 동일함을 확인합니다.

#### 16.9 기준 모델

##### Last-24h

예측 기준 `T` 직전의 실제 24시간을 다음 24시간 예측으로 사용합니다.

`ŷ(T+h) = y(T-24+h), h=1…24`

필요한 24시간 중 하나라도 결측이면 해당 평가 구간에서 사용할 수 없습니다.

##### Last-168h

예측할 각 시각의 168시간 전 실제값을 사용합니다.

`ŷ(T+h) = y(T+h-168), h=1…24`

대응하는 24개 실제값 중 하나라도 결측이면 해당 평가 구간에서 사용할 수 없습니다.

두 baseline은 GRU와 같은 비중복 Validation·Test 구간에서 평가하며 미래 실제값을 사용하지 않습니다.

#### 16.10 평가 지표와 모델 선택

핵심 지표:

- MAE: 기본 순위 지표
- RMSE: 큰 오차 민감도 확인
- WAPE: 전체 실제 사용량 대비 절대오차. 분모가 0이면 계산 불가로 표시
- MAPE: 실제값이 0인 시각을 제외하고 진단용으로만 계산하며 제외 개수 기록
- 예측 최소·최대·평균과 음수 예측 개수
- Peak MAE와 Peak Time Error는 보조 진단 지표

Validation 정책:

1. 같은 비중복 구간에서 GRU, Last-24h, Last-168h 지표 계산
2. MAE를 기본 순위로 사용
3. RMSE와 WAPE가 현저히 악화되지 않았는지 확인
4. 비유한 값 또는 음수 예측이 있는 GRU는 승격 후보에서 제외
5. 선택 결과와 근거를 Validation manifest에 고정
6. 이후 Test에서 순위가 바뀌어도 모델을 재선택하지 않음

GRU 승격 권장안:

- best baseline Validation MAE보다 최소 5% 낮음
- Validation RMSE와 WAPE가 best baseline보다 각각 5% 넘게 악화되지 않음
- 모든 예측이 유한하고 음수 예측이 없음

5% 개선 폭은 아직 PM 승인이 필요한 중요 정책입니다. 승인 전 구현은 지표와 추천 결과까지만 생성하고 active 모델을 자동 변경하지 않습니다.

#### 16.11 Test 평가 정책

- Validation에서 동결한 candidate와 두 baseline을 고정 Test 일정에서 평가
- Test는 최종 일반화 결과를 보고하기 위한 용도
- Test 결과로 candidate, 피처, scaler, hyperparameter 또는 체크포인트 변경 금지
- Test 실패 시 해당 run은 `TEST_FAILED`로 기록하고 승격하지 않음
- Test가 baseline보다 낮더라도 Validation 선택을 사후 변경하지 않고 새 실험 필요성을 보고
- Test를 개발에 다시 사용하면 이후 별도의 독립 Test 기간을 확보해야 함

#### 16.12 산출물과 버전 관리

권장 저장 구조:

`artifacts/{building_id}/{run_id}/`

`run_id`는 UTC 생성 시각, feature spec version, split version과 config hash를 포함하거나 이를 manifest에서 참조하는 불변 식별자입니다.

run별 필수 파일:

- `manifest.json`
- `training_config.json`
- `feature_spec.json`
- `split_manifest.json`
- `evaluation_schedule.json`
- `quality_report.json`
- `model_state_dict.pth`
- `input_scaler.pkl`
- `target_scaler.pkl`
- `validation_metrics.json`
- `test_metrics.json`
- `training_history.csv`

manifest 필수 항목:

- building ID와 run ID
- 모델·피처·분할 버전
- 입력·출력 shape
- IANA timezone
- 데이터 기간과 입력 해시
- scaler fit 기간과 통계 요약
- 설정값과 random seed
- 파일별 SHA-256
- Validation 선택 결과
- Test 상태
- run 상태와 생성 시각
- 라이브러리·CPU 환경 버전

기존 인턴 모델은 이 저장 루트로 복사하거나 덮어쓰지 않습니다. 신규 모델과 `legacy_reference`는 별도 경로·식별자로 관리합니다.

#### 16.13 승격·실패·롤백

- 학습 중간 산출물은 `staging` 상태
- Validation 선택과 Test가 끝나도 PM 승인 정책을 충족하기 전에는 `candidate`
- 운영 모델은 별도 `active_model.json` 포인터가 특정 불변 run을 참조
- 승격은 새 run을 덮어쓰지 않고 active pointer만 원자적으로 변경
- 실패한 run은 `FAILED` 상태와 실패 단계·오류를 기록하고 active pointer를 변경하지 않음
- 롤백은 이전 정상 run으로 active pointer를 되돌리는 방식
- 산출물 식별자, 피처 순서, scaler, model hash가 하나라도 다르면 로딩 거부
- 모델 파일은 신뢰된 로컬 산출물만 안전한 가중치 로딩 옵션으로 읽음

재학습 트리거, 자동 승격 여부, 보존할 이전 버전 수와 롤백 권한은 후속 결정 사항입니다.

## 17. Phase 7-4 구현 보완

### 17.1 시간대 출처 모드

모든 신규 run manifest는 `source_timezone_mode`를 저장합니다.

| 값 | 적용 대상 | 규칙 |
|---|---|---|
| `iana_civil_time` | 시간대 없는 일반 사용자 CSV | `building_timezone`의 실제 DST 규칙으로 현지화 |
| `explicit_offset` | ISO 8601 offset 포함 CSV | 각 timestamp의 offset을 기준으로 UTC 변환 |
| `bdg2_naive_local_grid_fixed_standard` | BDG2 전용 | DST 중복·누락 없는 원본 격자를 `Etc/GMT±N` 고정 offset으로 보존 |

BDG2 모드는 offset-naive 입력과 고정 offset feature timezone만 허용합니다. 일반 IANA 처리와 같은 함수 호출에서 암묵적으로 전환하지 않습니다. 신규 manifest에는 원본 시간대인 `source_timezone_metadata`와 피처 계산 시간대인 `feature_timezone`을 구분해 기록합니다. 기존 `building_timezone`은 `feature_timezone`의 호환 별칭으로 유지하며, 과거 run에 새 필드가 없으면 loader가 메모리상 `building_timezone`으로 fallback하고 원본 manifest는 수정하지 않습니다.

### 17.2 Train 0분산 차단

Train 고유 timestamp의 kWh가 모두 동일하면 scaler 적합과 `train_gru` 호출 전에 `FAIL_TRAIN_ZERO_VARIANCE`로 중단합니다. Validation/Test에 변화가 있더라도 Train이 학습할 변화 정보를 포함하지 않으므로 학습을 허용하지 않습니다.

### 17.3 분포 이동 진단

Train, Validation, Test별 관측 수·평균·표준편차와 Train 표준편차로 나눈 평균 이동량을 저장합니다. 1.0 이상은 WARNING입니다. 이 결과는 진단과 사용자 안내용이며 모델 선택 규칙이나 Test 독립성을 변경하지 않습니다.
